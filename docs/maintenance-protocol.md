# Infinite Canvas 持久维护协议

## 目的

聊天上下文是临时的，Git 和仓库文档是持久的。后续任务应从仓库重建上下文，而不是要求用户重述全部历史。

## 证据层级

1. `AGENTS.md`：执行规则和安全边界。
2. `docs/change-records/INDEX.md`：短索引，用于按日期、模型、文件和症状定位记录。
3. `docs/change-records/<year>/...`：单次变更的需求、实现、测试、风险和回退证据。
4. `docs/decisions/`：不应被无意破坏的长期设计约束。
5. Git 提交：每一行实际改动。
6. `data/task_logs.sqlite3`：本机实际 API 运行时证据，不进入 Git。

## 新任务如何恢复上下文

1. 查看当前版本和未提交文件。
2. 在变更索引中搜索当前症状、模型名、端点或文件名。
3. 只读取命中的 1–3 份记录和相关决策。
4. 用记录中的提交哈希执行 `git show`，与当前代码对比。
5. 有 Trace ID 时查看详细 API 日志，将运行事件与源码版本对齐。

## 单次变更的提交节奏

1. 实施提交：代码、测试和必要的用户文档。
2. 记录提交：变更档案与索引，引用实施提交的完整哈希。
3. 发布：推送工作分支，验证远程哈希；需要更新 `main` 时只做安全的快进合并或经审查的合并。

文档提交不需要为自己再生成一份递归记录。

## 故障处理

1. 先诊断，未经用户授权不直接实施修复或回退。
2. 区分配置/上游故障、运行数据故障和源码回归。
3. 建立最小复现，用新增测试锁定症状。
4. 按变更记录列出候选提交，再用对比或二分定位验证。
5. 报告“有证据的原因”与“尚未排除的可能性”，不混为一谈。

## 数据与凭据

变更记录中可以记录字段名、脱敏的请求结构和凭据故障类型，但不得记录任何实际 API Key、Token、Cookie、私钥内容或用户图片内容。
