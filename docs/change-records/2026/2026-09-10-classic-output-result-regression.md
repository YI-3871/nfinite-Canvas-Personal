## 用户需求与修改前现象

用户和同事在传统画布使用 API 图像生成节点时均遇到同一问题：OUTPUT 节点在生成期间正常显示运行状态，但任务完成后节点变为空白，没有任何生成图。用户于 2026-09-10 上午连续生成两次均复现。

用户同时确认详细 API 日志入口不易发现。当前 UI 入口仍为画布右上角“日志”，打开后顶部选择“浏览详细日志”，单条摘要也可选择“API 详情”。本次浏览器验证确认传统画布与智能画布入口均存在且可见，因此没有修改日志 UI。

## 根本原因

这是 `0dbf2e3e2744d25deb8b08971b504387393aa507` 引入的传统画布前端回归。

为了让颜色保护后的 `raw_url`、`trace_id` 和诊断元数据跟随图片返回，该提交把传统画布多个完成路径从直接读取 `result.images` 改成将 `result.image_items` 或 `result.images` 数组传给 `resultMediaUrls()`。但是该解析器只遍历传入对象的命名属性，没有先处理传入值本身；数组作为最外层参数时没有这些命名属性，因此被错误解析为 0 张图片。

直接证据：

- 两条 Trace 均为 `succeeded/completed`，耗时分别约 65.5 秒和 79.2 秒。
- 后端响应分别包含一张普通输出和一张颜色保护输出，`images` 与 `image_items[].url` 均有有效本地地址。
- 三个相关 PNG 文件均存在、可解码且尺寸有效；问题不在上游模型、颜色保护或文件落盘。
- 同一画布持久化结果中，两条摘要均为 `success` 但 `outputs` 数量为 0，OUTPUT 节点的 `images` 数组为空。
- 修复前最小测试中，`resultMediaUrls([imageItem])` 和 `resultMediaUrls([url])` 均返回 0 项；传入完整结果对象可返回 1 项。

## 验收标准

- [x] `image_items` 对象数组作为最外层输入时能解析出图片。
- [x] 普通 URL 字符串数组作为最外层输入时能解析出图片。
- [x] 完整 API 结果对象能去重，优先保留带元数据的 `image_items`。
- [x] 解析后的图片可写入传统画布 OUTPUT 节点。
- [x] `raw_url`、`trace_id` 和 `color_preservation` 元数据保留。
- [x] 不增加 API 请求、图片下载、解码或颜色保护步骤。
- [x] 智能画布和详细日志入口保持原有行为。

## 实施方案

1. `resultMediaUrls()` 先调用内部递归解析器处理根输入，使对象、数组和字符串都使用同一解析路径。
2. 五个传统画布 API 完成、恢复和兼容路径统一把完整结果对象交给解析器，不再由调用者提前挑选数组字段。
3. 继续按最终 URL 去重；完整结果同时包含 `image_items` 和 `images` 时，保留先出现且元数据更完整的 `image_items`。
4. 新增 Node.js 回归测试，直接从实际 `canvas.js` 加载解析与 OUTPUT 写入函数，防止测试复制一份与生产代码分离的实现。

- 不需要数据迁移。

- 既有生成文件和详细 Trace 不会被修改或删除，可按 Trace 找回并重新加入画布。

## 安全、隐私与资源影响

- 不读取或记录新的凭据、提示词、图片内容或 Base64。
- 不增加网络请求、API 调用、图片下载、图片解码或颜色处理。
- 解析器只遍历已经返回到浏览器的小型结果结构，并继续按 URL 去重；相对 65–79 秒的生成过程没有可感知延迟。
- 没有改变 SQLite、Python 内存任务缓存或画布摘要上限。

## 故障排查入口

- 任务成功但 OUTPUT 为空：先在“日志 → API 详情”确认响应是否包含 `image_items` 或 `images`，再检查浏览器实际加载的 `canvas.js` 版本。
- 验证本回归：运行 `node --test tests/test_canvas_result_media_urls.js`。
- 查找引入与修复差异：对比提交 `0dbf2e3e2744d25deb8b08971b504387393aa507` 和 `cf50ac4dfca7df9f921c36236d48d8d8829e97c4` 的 `static/js/canvas.js`。
- 如果只有旧任务为空而新任务正常，这是预期：源码修复不会篡改已经保存的画布运行数据。
