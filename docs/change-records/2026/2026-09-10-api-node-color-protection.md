## 用户需求与修改前现象

颜色保护原先只有在模型名称以 `gemini-3.1-flash-image` 开头时才显示和执行。用户通过中转站调用同一模型时，中转站可能把模型命名为 `nano-banana-2` 或其他自定义名称，导致 API 生成节点不显示任务类型与颜色保护，后端即使收到颜色保护参数也会因名称不匹配而跳过处理。

用户要求把颜色保护固定在 API 生成节点中，其他行为保持不变。

## 根本原因或实施假设

根本原因由代码确认：

- 传统画布在 `static/js/canvas.js` 中根据模型名前缀切换颜色保护行的 `display`。
- 智能画布在 `static/js/smart-canvas.js` 中仅为匹配该前缀的模型渲染任务类型和颜色保护控件。
- 后端 `main.py` 同时用相同前缀决定参数 schema 是否包含控件，以及是否真正调用颜色保护算法。

中转站模型别名不具备可依赖的统一命名规则，因此不能通过扩充别名列表稳定解决。

## 验收标准

- [x] 传统画布 API 生成节点在 `nano-banana-2` 和任意自定义模型名称下都显示任务类型与颜色保护。
- [x] 智能画布 API 图片生成面板在任意模型名称下都显示并可切换颜色保护。
- [x] 后端参数 schema 对 API 图片生成固定返回任务类型与颜色保护字段。
- [x] 中转别名请求在选择“自动”或“严格”后可以进入颜色保护处理，不再因模型名称跳过。
- [x] 默认值仍为“关闭”，原图保留、低置信度回退、异常回退和 `scene_change` 行为不变。
- [x] 不调用真实付费 API，不修改其他类型节点。

## 实施方案

1. 传统画布直接渲染原有颜色保护行，删除模型切换时的可见性判断。
2. 智能画布在 API 图片参数区无条件渲染原有任务类型与颜色保护控件。
3. 后端对 `api` / `volcengine` 图片参数固定提供两个字段；当用户选择 `auto` 或 `strict` 且原图与参考图均可解析时，直接执行现有本地颜色保护管线。
4. 保留既有字段、默认值、诊断结构、原图与校正图输出方式，没有数据迁移。

## 安全、隐私与资源影响

- 默认关闭，因此仅打开画布或切换模型不会增加图像处理开销。
- 用户对任意 API 模型主动选择“自动”或“严格”后，会执行既有本地颜色分析并可能生成 `_colorfix` 附加文件；原始输出仍保留。
- 没有扩大网络访问、凭据读取、日志内容或外部权限范围。
- 内存、磁盘上限、日志脱敏和异常安全回退保持原实现。

## 未验证内容与已知限制

- 未对每一家中转站分别发起真实请求；中转站只要仍返回可保存的图片，颜色保护本地后处理不依赖其模型名称。
- 无参考图、低置信度、场景/光线任务或算法异常仍会按既有规则直出原图。

## 故障排查入口

- API 生成节点仍不显示颜色保护 → 确认浏览器已加载当前 `canvas.js` / `smart-canvas.js`，检查缓存与页面错误。
- 选择“自动/严格”但没有 `_colorfix` → 用 Trace ID 查看 `color_protection` 阶段的 `reason`、`confidence`、参考图地址与安全候选结果。
- 怀疑模型别名再次被限制 → 运行 `tests/test_main_features.py` 中的模型无关 schema、前端固定渲染和别名执行测试。
